# 博客前端发布与回退

本流程只更新博客前端，不更新后端、管理后台或数据库。当前版本须先通过本地与 CI 验证，再单独授权实际发布；本文命令没有在生产服务器执行。

## 构建和候选版本

- 提交完整的前端源码、锁文件与 `public/study-assets`，使用该提交的 SHA 标识候选版本。
- `.github/workflows/deploy-blog.yml` 仅手动触发，默认 `deploy=false`：运行前端测试、类型检查、生产构建、standalone 打包和生产服务冒烟，上传制品，不上线。
- 需要实际上线时，在已批准的提交上选择 `deploy=true`，经过 `production` 环境权限/审批后部署。同一个工作流复用验证过的制品，不在服务器重建。
- 原 `deploy.yml` 已改为仅手动触发，防止普通前端提交自动运行全栈部署和数据库迁移。全栈发布仍需明确选择该工作流。
- 使用 CI 的 Linux 产物部署；Windows 本地产物仅用于本地验收。

## 首次启用的前提

1. 服务器符合现有 `deploy-remote.sh` 的 systemd 结构：用户 `myblog`、根目录 `/home/myblog`、服务 `blog-web.service`、端口 3001，已有 `/home/myblog/current/blog/server.js`。若实际为 PM2 或不同目录，先调整流程，脚本不猜测并修改未知服务。
2. Nginx 主站配置文件默认 `/etc/nginx/sites-available/www.new-universe.cn`；实际位置不同时通过 `NGINX_SITE` 明确指定。需要启用 `www.new-universe.cn` HTTPS 虚拟主机；证书和原有配置继续保留。
3. GitHub 的 SSH 凭证、主机指纹和生产环境规则已设置；部署账号有现有部署脚本所需的 root 权限。凭证不写入制品。
4. 保留前端旧产物与可用磁盘，不在此次发布中清理历史版本。确认旧的全栈清理流程不会删除前端回退还引用的目录。

## 代理分流

`/api/study/` 保持完整路径转给 Next.js 端口 3001；其他 `/api/` 继续使用原后端路由。`^~` 避免文件扩展名规则截走接口。

`/study-assets/` 使用重新验证缓存；Next 的构建哈希文件仍长期缓存。更新图片不要求访客手动清缓存。

脚本在指定虚拟主机内添加缺失规则，保留其他主机、TLS 和后端规则。先备份，再执行 `nginx -t`；错误时恢复旧配置。已有同名规则的实际 upstream 仍应在首次上线前核对，经代理 JSON 冒烟可拦截指向错误服务的问题。

## 版本切换

新版本放在 `/home/myblog/blog-releases/<时间>-<提交>/`，由独立的 `blog-current` 指针选择。systemd 仅增加前端工作目录覆盖项，重启 `blog-web.service`。`current/` 原全栈指针保持原样。

standalone 包同时兼容根入口与嵌套入口，静态文件和 public 放在真实应用入口旁。每个版本提供 `blog-release.json`，检查时确认服务返回当前提交，而不是旧页面恰好返回 200。

切换后检查：首页、中英文、阅读、搜索、非法查询、图片及版本号；再通过真实 Nginx HTTPS 虚拟主机检查接口 JSON 与版本号。任何失败恢复旧指针、systemd 覆盖项和 Nginx 配置，只重启前端。

## 手动回退

在服务器上，保留发布时使用的脚本，通过 `bash deploy-blog.sh rollback` 回到当前版本记录的上一前端目录。默认目录不同时传递相同 `APP_HOME`。回退失败会切回原先当前版本。

旧版本不删除，发布日志记录旧目录和配置备份。首次上线后如果再运行旧全栈发布流程，需要先统一它对前端指针和历史清理的处理；不要混用两套版本选择方式。

## 验证边界

本地 helper 测试验证根/嵌套打包、public/static 位置、环境文件排除、重复输出保护、Nginx 分流和重复补丁。Bash 语法检查不能替代真实服务器上的 systemd/Nginx 验收。

CI 工作流已经包含干净安装和 standalone 生产模式冒烟，但未触发 CI 不等于 CI 已通过。当前聊天之前被拒绝的生产服务启动或浏览器操作，不通过间接方式重试绕过；涉及该权限的验收继续单独记录。
