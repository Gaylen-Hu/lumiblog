# 杭州窗景与书房环境系统：需求审核及开发计划

日期：2026-11-05

版本：1.0（需求审核稿）

状态：完成需求与现有代码的对照审核；后续实施已开始，实际完成范围见[推进记录与交接](environment-progress/README.md)。本文描述目标范围，不表示全部功能或素材已经完成。

审核基线：本地工作区，Git HEAD `5fe012b`；同时参考工作区现有书房设计资料。
默认地点：杭州，`Asia/Shanghai`（UTC+8），城市代表坐标约 `30.2741, 120.1551`。

后续用户确认：**“窗外花园 + 柔和暖色书房”正式沿用**；专用和风测试账号已完成真实 HTTP 200 验证。凭据不写入本文，详细结果见推进记录。

## 1. 审核结论

需求具备可行性，适合在现有 Next.js、Three.js、NestJS、Redis 架构上增量实现。核心产品应定义为：**一扇随博主所在地时间、天气和季节变化的窗，带动室内光照变化，并允许访客临时选择喜欢的氛围。**

建议分两次交付：

- **首版**：杭州配置、四时段、晴／多云／阴／雨、玻璃雨滴、雨声、手动预设、后台配置、天气代理与缓存、失败回退、移动端降级。
- **扩展版**：四季正式植被、雪、雾和更细的天气过渡。首版必须预留季节与雪的状态接口，但不以未完成的正式雪景作为首版上线条件。

上一版构想需要以下修正，不能直接当作开发验收标准：

| 编号 | 审核发现 | 修正决定 | 优先级 |
| --- | --- | --- | --- |
| A01 | 当前昼夜及挂钟使用浏览器本地时间，异地访客看到的不是杭州时间 | 统一时间服务；杭州时区驱动挂钟、时段和月份；不改变文章原有时间展示规则 | 首版前置 |
| A02 | 当前台灯开关会切换全屋昼夜，而非只开关灯 | 分离环境时段、台灯状态和访客预设；点击台灯不改变天空、挂钟或天气 | 首版前置 |
| A03 | 现有窗外是贴图远景，不能假设已经有可折射的玻璃和分层室外场景 | P0 检查窗洞、材质、遮挡及相机；先完成雨夜原型，再决定折射技术细节 | 首版前置 |
| A04 | “当前天气”接口不一定提供日出日落，不能用一个接口假设覆盖所有字段 | 实时天气与当日日出日落分开获取、缓存；后者可由本地太阳计算替代 | 首版前置 |
| A05 | 把天气缓存 TTL 设为 15 分钟会导致过期后没有旧数据可回退 | 新鲜期与保留期分开：建议新鲜 15 分钟、最多保留 2 小时；按数据时间校验 | 首版前置 |
| A06 | 冬天不等于下雪，下雪不等于地面已经积雪 | 自动模式按天气码决定降雪；厚积雪只用于明确的手动预设或有依据的数据状态 | 扩展版前置 |
| A07 | 雨滴效果演示不是可直接投产的 React 组件 | 核验授权；在现有 renderer 中封装窗玻璃材质，禁止为演示方便新增第二套全屏渲染器 | P0 验证 |
| A08 | 原方案的路由是示意，没有体现现有 `/v1/public` 与 Nginx 转发规则 | 复用实际配置体系及版本化路由，不另起平行配置中心 | 首版前置 |
| A09 | 动态雨雪会打破房间空闲时低频绘制策略 | 扩展同一个渲染调度器，定义窗口不可见、阅读、轻量、减少动态时的暂停条件 | 首版前置 |
| A10 | 原方案没有明确手动预设的保存范围、恢复规则与状态文案 | 访客预设按当前标签页会话保存；后台预设作为站点默认；实时／缓存／预设／回退分别标注 | 首版前置 |
| A11 | 现有公开 site-config 与前端读取均有一小时缓存，不适合天气快照 | 环境使用独立配置服务与公开接口，后台仍复用原设置页面入口 | 首版前置 |
| A12 | 现有设置写接口的 JWT 认证不等于管理员授权；也不能仅因导入限流模块就认为已启用限流 | 环境写接口显式检查管理员权限，公开接口落实限流；不继承未经验证的安全假设 | 首版前置 |
| A13 | 和风新版与旧城市版的端点、单位和字段不同，旧域名正在迁移 | 明确选定接口版本及专属 API Host；用真实响应样本建立映射，不混用旧版解析 | P2 前置 |

本文所有缓存时长、动画时长、资源预算和人日估算均为建议初值，需要在 P0 和设备实测中校准；城市、时区、天气分类、异常不阻塞阅读等产品约束应进入正式验收。

## 2. 最终体验

### 2.1 默认体验

1. 访客打开博客，现有书房和内容入口正常出现；天气请求不阻塞首屏、目录和文章。天气来源在信息区域提供清晰可见链接。
2. 环境默认跟随博主杭州的时间与天气，不申请访客地理定位。
3. 窗边保留低干扰状态入口，例如“杭州 · 17:42 · 小雨”。声音初始关闭。
4. 点击入口后展开环境面板，首版选择“跟随站点默认”或已发布的氛围预设；站点默认是自动模式时显示“跟随杭州”。自由组合天气、时段、季节留作扩展。
5. 打开文章后保持阅读体验，背景粒子按阅读状态暂停或降低开销。用户明确开启的雨声可以继续，提供随时静音入口。
6. 返回房间仍是同一个 Three.js 场景；读取当前时间和最新有效状态，不重建整间书房。

状态文案示例中的温度和时间仅说明交互，不是天气实况：

| 状态 | 文案示例 | 行为 |
| --- | --- | --- |
| 自动、新鲜 | 杭州 · 17:42 · 小雨 | 展开可查看天气来源与更新时间 |
| 使用旧缓存 | 杭州 · 小雨 · 获取于 17:30 | 明确标示更新延迟，保留正常窗景；有供应商观测时间时可另行标注 |
| 访客预设 | 氛围预设 · 雨夜 | 不伪称杭州正在下雨；可一键恢复站点默认 |
| 博主预设 | 博主预设 · 冬日飘雪 | 明确不是实时天气 |
| 无有效数据 | 杭州 · 天气暂不可用 | 保留杭州时段，使用中性窗景，不显示虚构温度 |

### 2.2 代表性效果

| 场景 | 窗外与天空 | 玻璃与粒子 | 室内响应 |
| --- | --- | --- | --- |
| 春日清晨 | 淡蓝天空、嫩绿树冠、轻微晨雾 | 干净玻璃，弱反光 | 偏暖的低角度晨光，较长窗框影 |
| 夏日晴午 | 明亮天空、浓绿树冠，细微风动 | 弱反射，无雨滴 | 明确但不过曝的窗框投影；东窗直射受朝向限制 |
| 秋日黄昏 | 黄绿混合植被，暖色天边逐渐转蓝 | 少量暖色环境反光 | 夕光减弱，台灯成为视觉中心 |
| 冬日阴天 | 冷灰天空、稀疏枝叶 | 微弱冷色反射 | 柔和漫射光与暖台灯；不自动积雪 |
| 安静雨夜 | 深蓝远景、少量远处灯光 | 水滴聚合、下滑、水痕与局部折射 | 室外暗，室内暖；用户开启后有低音量雨声 |
| 冬日飘雪 | 分远近缓慢飘雪，远景低对比 | 玻璃边缘可有少量冷雾 | 冷漫射光、暖室内；积雪只在预设中独立启用 |

过渡建议：普通光照与天气变换约 3～8 秒；雨停后雨线先减少，玻璃水滴再逐渐淡出。减少动态效果模式直接应用静态终态，不播放长过渡。

### 2.3 当前不纳入

首版不做逐滴流体模拟、准确室内热湿计算、物理积雪增长、真实道路反光、自由行走、新一套房间模型、强闪雷电、昼夜驱动的宠物行为。后续可通过同一环境状态接入宠物，但不能成为天气系统的依赖。

## 4. 配置、时间与状态规则

### 4.1 博主配置

| 字段 | 默认／规则 |
| --- | --- |
| 城市显示名 | 杭州；可提供中英文显示名 |
| 纬度／经度 | `30.2741 / 120.1551`，验证范围；允许博主选择粗粒度代表点 |
| 时区 | `Asia/Shanghai`，使用 IANA 时区标识，不只存 `+8` 字符串 |
| 站点环境模式 | `auto` 或 `preset` |
| 站点默认预设 | 非自动模式时生效；必须是已发布的预设 ID |
| 季节模式 | `calendar` 或 `manual`；首版仅保留配置与基础色板 |
| 台灯偏好 | `auto/on/off`，与环境时段分开 |
| 音频可用 | 只控制是否提供雨声功能，不授权自动播放 |
| 环境功能开关 | 关闭后仍可进入普通书房／阅读回退界面 |
| 供应商凭据 | 仅部署侧保管；公开配置与前端表单均不回传原值 |

改变城市／坐标／天气源时使用新缓存键，不能将杭州旧天气展示给新城市。保存配置后使旧公开配置缓存失效；通过配置版本防止迟到响应覆盖新配置。

### 4.2 统一时间

- 绝对时间以 UTC 时间戳传输；时区只用于解释当地日历、时分秒和显示。
- 使用 `Intl.DateTimeFormat(..., { timeZone: 'Asia/Shanghai' })` 等显式时区能力取得日历分量，不用日期字符串往返解析冒充时区转换。
- 接口返回当前请求的 `serverNow`；不得复用 15 分钟前缓存快照中的时间作为当前时间。
- 客户端可估算服务端时间偏差并以单调计时推进；回前台、设备休眠恢复和重新联网时重新校正。
- 后端不可用时使用设备当前绝对时间和配置时区；说明此时不保证纠正访客设备自身的错误时钟。
- 挂钟始终表示真实的杭州时间。选择“雨夜”预设只改变环境氛围，不把挂钟拨到虚构的 22:00。
- 自动模式的“现在几点”和预设模式的“看起来是什么时段”是不同字段。

### 4.3 四时段

以当天当地日出 `R`、日落 `S` 为基准，建议使用以下产品区间：

| 时段 | 区间 | 光照特征 |
| --- | --- | --- |
| 晨间 `morning` | `[R−30 分钟, R+90 分钟)` | 淡金、低角度、由弱渐强 |
| 白昼 `day` | `[R+90 分钟, S−60 分钟)` | 中性日光；按朝向控制直射 |
| 黄昏 `dusk` | `[S−60 分钟, S+30 分钟)` | 暖色逐渐转冷，室外变暗 |
| 夜晚 `night` | 其余时间 | 深蓝环境光，台灯和室内补光主导 |

区间为半开区间，边界只归属一个状态。实际光照消费连续进度和角度，不能在边界瞬间换一整套灯光。

日出日落获取顺序：当天有效天文数据 → 本地按经纬度计算 → 固定表回退（建议晨间 06:00～08:00、白昼 08:00～17:00、黄昏 17:00～19:00、夜晚其余时间）。固定表回退只说明表现规则，不宣称是当日日出日落。

首版只要求杭州；配置允许其他城市时，对无日出／无日落、异常区间及当地日期跨日做兜底，不能产生负时长或 `NaN`。

### 4.4 季节

自动季节按博主当地月份：春 3～5 月、夏 6～8 月、秋 9～11 月、冬 12～2 月。这是杭州的美术季节规则，不是物候实测，也不能直接当成全球城市通用规则。

- 春：嫩绿、少量花色；避免持续樱花雨。
- 夏：深绿、树冠丰满；可有克制的叶片摆动。
- 秋：绿黄混合、少量落叶；落叶是可关的效果，不必全场持续运行。
- 冬：枝叶稀疏、远景偏冷；不由月份自动触发下雪或积雪。
- 预设可以覆盖季节；“恢复自动季节”只清除季节覆盖，不应意外改变雨声偏好。
- 月份边界使用短暂交叉淡化即可；长期物候渐变属于后续增强。

### 4.5 优先级与保存范围

环境状态解析顺序：系统有效默认值 → 博主自动／预设配置 → 访客临时覆盖；天气获取失败只影响自动天气分支。

| 状态 | 保存位置 | 生效范围 | 清除／恢复 |
| --- | --- | --- | --- |
| 博主配置 | 服务端站点设置 | 所有访客的默认环境 | 后台修改并刷新配置版本 |
| 访客环境预设 | `sessionStorage` | 当前标签页会话；刷新后可恢复 | “恢复站点默认”清除；城市配置变更时丢弃不兼容覆盖；复制标签页可能继承初值，之后独立 |
| 访客音量／静音偏好 | 可用时 `localStorage` | 同一浏览器 | 用户修改；跨会话仍需满足播放手势要求 |
| 台灯手动状态 | 当前会话 | 只影响本人的灯 | 切回台灯自动或恢复站点默认 |
| 帧率自动降级 | 内存状态 | 当前场景实例 | 用户重新选择自动时可重试，避免自动来回跳档 |

预设定义为若干字段的补丁，未覆盖字段继续跟随站点规则。首版提供完整预设，不要求 UI 开放所有自由组合；高级组合可以后补。

所有“恢复自动／默认”的文案应明确目标：后台如果启用了博主预设，访客应看到“恢复站点默认”，不能承诺一定恢复实时天气。

## 5. 天气数据与开放接口

### 5.1 选型结论

建议和风天气作为正式主源候选；Open-Meteo 作为原型或有条件的备用候选。首版仅实现一个生产供应商，保留适配接口，不做双源自动轮询。

| 项目 | 和风天气 QWeather | Open-Meteo |
| --- | --- | --- |
| 查询方式 | 城市标识或经纬度，具体遵循对应接口 | 经纬度查询 |
| 凭据 | 当前支持 JWT 与 API Key；服务端使用 | 免费非商业公共端点通常无需 Key；商业服务按当前方案接入 |
| 需要的数据 | 当前天气；另取当日日出日落 | 当前天气变量和 daily 日出日落 |
| 数据含义 | 保留供应商原始更新时间和字段语义 | 当前天气源于天气模型，不标为现场传感器实测 |
| 生产条件 | 验证账号、API Host、可用产品、配额、署名与许可 | 核对免费非商业限制、商业方案及 CC BY 4.0 署名 |
| 可靠性判断 | 国内服务器实际请求测试后决定 | 同样测试国内部署节点的连通性、超时和更新间隔 |

不在需求文档中固定价格、免费额度或承诺免费商用；以开通时的官方方案和账号权益为准。博文站点是否属于商业使用需按供应商定义判断，不能仅因访问量小而自行认定。

和风接口版本实施约束（2026-11-05 官方文档核验）：

- 新版实时天气：`GET /weather/v1/current/{latitude}/{longitude}`。
- 新版逐日预报：`GET /weather/v1/daily/{latitude}/{longitude}?days=1`，包含日出日落。时间默认 UTC，按接口要求处理 `localTime` 参数；建议内部统一 UTC。
- 新版路径坐标顺序是**纬度、经度**。不要沿用旧城市版参数中经纬度组合的顺序。
- 新版响应的风速示例单位是 `m/s`，云量示例是 `0..1`；旧版解析器可能使用其他单位或范围，必须读单位和当前字段定义。
- 官方新版实时示例没有旧版 `obsTime` 字段；适配层不得假定该字段必有，也不得用抓取时间伪造观测时间。
- 使用控制台分配的专属 API Host。官方说明旧共享域从 2026 年起逐步停用，不在代码中硬编码旧共享域。
- 使用和风数据须按适用条款提供可见署名及 QWeather 链接；Open-Meteo 同样需要在数据展示附近提供来源链接。具体放置位置在 P0 的状态 UI 中落实。

对应官方依据：[新版实时天气](https://dev.qweather.com/en/docs/api/weather/weather-current/)、[逐日预报](https://dev.qweather.com/en/docs/api/weather/weather-daily-forecast/)、[API Host](https://dev.qweather.com/en/docs/configuration/api-host/)、[和风署名规则](https://dev.qweather.com/en/docs/terms/attribution/)。Open-Meteo 的数据许可与免费托管服务使用条件分别见[数据许可](https://open-meteo.com/en/licence)和[服务条款](https://open-meteo.com/en/terms)，不能用开放数据许可推导免费 API 可以商业使用。

### 5.2 供应商适配契约

统一输出，前端不消费供应商天气码：

| 字段 | 规则 |
| --- | --- |
| `condition` | `clear/cloudy/overcast/rain/snow/fog/thunderstorm` |
| `precipitationKind` | `none/rain/snow/mixed`，为雨夹雪预留 |
| `intensity` | 归一化 `0..1`，映射表可配置；不把缺失值当作强降水 |
| `temperatureC` | 摄氏度，可为 `null` |
| `windSpeedMps` | 统一为米／秒；UI 如展示其他单位需显式转换 |
| `windDirectionDeg` | 可选；气象“来向”需转换成场景坐标，不能直接当粒子运动方向 |
| `cloudCover` | 可选 `0..1`，供应商无字段时使用保守类别默认值 |
| `observedAt` | 供应商观测／模型有效时间，UTC；没有时为 `null`，与抓取时间分开 |
| `fetchedAt` | 服务端实际取得数据的时间 |
| `provider` | 来源标识和所需署名信息 |

天气码必须完整映射。首版遇到雾、雪、雷雨但相应正式效果未完成时，保留真实天气标签，视觉用中性阴天或雨景近似；不能将“雪”改成“晴”来掩盖未实现。

雨夹雪首版可显示正确文字，使用较保守的雨景；扩展版支持混合粒子。未知码、必需字段缺失、单位错误、明确提供但异常的时间、过旧时间、HTTP 200 但业务错误均作为适配失败处理。供应商合法不提供观测时间不等于错误，此时 UI 只能标“获取于”，不能标“观测于／实况更新于”。

### 5.3 日出日落单独管理

- 不假设实时天气响应携带日出日落；和风需要对应逐日天气／天文能力，具体按官方接口返回。
- 缓存键包含城市坐标、时区与当地日期；过了当地午夜不能直接把昨天的日出日落当今天使用。
- 天文数据与实时天气独立缓存，天气接口失败不必使当天有效日出日落失效。
- 本地太阳计算依赖在 P0 选型，要求可测、时区语义清楚；不为此引入一整套天气 UI SDK。

### 5.4 代理与缓存

链路：浏览器 → 本站公开环境接口 → 天气服务 → Redis／供应商。浏览器不直接请求带密钥的天气服务。

建议初值：

| 参数 | 建议 | 语义 |
| --- | --- | --- |
| 天气新鲜期 | 15 分钟 | 期内直接使用，仍检查供应商数据时间 |
| 旧天气保留期 | 最多 2 小时 | Redis 物理保留期长于新鲜期；旧数据必须标记 |
| 上游超时 | 约 4 秒 | 到时中止请求，不拖住整个书房 |
| 前端刷新 | 可见时约 15 分钟，带少量随机偏移 | 只刷新本服务；回前台按新鲜度决定是否立即刷新 |
| 失败退避 | 1／5／15 分钟，设上限 | 遵循供应商限流提示，不在每次页面请求中重试 |
| 公开配置刷新 | 建议不超过 60 秒 | 后台保存主动失效；不等天气新鲜期才更新配置 |

缓存记录包含 `schemaVersion/provider/locationKey/observedAt/fetchedAt/freshUntil/staleUntil`。是否可用检查抓取时间，并在供应商提供有效时间时同时检查数据年龄，禁止不断重新抓取同一条明确过旧数据而无限延长“实况”。无观测时间时采用保守抓取新鲜期，明确时间标签，不能承诺判断供应商内部数据的真实年龄。缓存建议须符合当前供应商条款；2 小时只代表本项目愿意保留的旧数据上限，不代表供应商保证实时性。

并发与异常要求：

1. 新鲜缓存命中直接返回；过期但仍可用时，返回标记过期的快照，并触发受控后台刷新。
2. 同一进程用 single-flight 合并刷新；多实例部署用 Redis 短锁协调，带过期和持有者校验，避免误删其他实例的锁。
3. 首次无缓存的请求可以短暂等待共享刷新，但前端已经展示默认窗景，内容不等待天气。
4. Redis 不可用时使用有界进程内缓存、请求合并和退避；不能把所有并发访客直接透传给供应商。多实例 Redis 故障时允许直接回退以保护配额。
5. 刷新失败不覆盖最近成功数据；达到保留上限才转为回退状态。
6. 天气缓存不缓存“现在几点”；接口的 `serverNow` 由当前请求即时生成。
7. 公开 HTTP 层首版沿用站点 `no-store` 策略，天气缓存只在服务端控制。未来增加 CDN 缓存必须重新处理状态年龄与服务端时间。
8. 运行期 Redis 降级属于本模块承诺；整个后端在 Redis 不可连接时能否冷启动，由现有模块初始化决定，需要另外测试和必要改造，不用前端回退掩盖服务启动失败。

## 6. 环境状态与公开接口

### 6.1 分离数据状态与视觉状态

不能只用一个 `source` 字段同时表达“天气来自旧缓存”和“用户正在看雨夜预设”。建议分为：

- `WeatherSnapshot`：真实天气、数据来源、有效时间和新鲜度。
- `SiteEnvironmentConfig`：城市、时区、模式、预设及版本。
- `VisitorOverrides`：当前访客选择，不发送到共享公开缓存。
- `ResolvedEnvironment`：合成后的视觉参数、声音意图、说明文案。

建议核心类型示意，最终名称按代码规范调整：

```ts
type Phase = 'morning' | 'day' | 'dusk' | 'night'
type Season = 'spring' | 'summer' | 'autumn' | 'winter'
type Condition =
  | 'clear' | 'cloudy' | 'overcast'
  | 'rain' | 'snow' | 'fog' | 'thunderstorm'

type ResolvedEnvironment = {
  phase: Phase
  phaseProgress: number
  season: Season
  condition: Condition
  precipitationIntensity: number
  windSpeedMps: number
  temperatureC: number | null
  visualMode: 'automatic' | 'owner-preset' | 'visitor-preset' | 'fallback'
  weatherFreshness: 'fresh' | 'stale' | 'unavailable'
  lamp: 'auto' | 'on' | 'off'
  presetId: string | null
}
```

雨滴数量、太阳色温、雾密度等由视觉参数表从统一状态派生，业务 API 不需要传每个 shader uniform。

### 6.2 路由与返回规则

规划公开接口：`GET /v1/public/environment`，延续现有公开接口体系。浏览器通过已有 API 基址访问；经过当前 Nginx `/api/` 转发时，外部路径为 `/api/v1/public/environment`，由反向代理剥离 `/api`。部署前用实际配置验证，不硬编码另一套 `/api/environment`。

返回信息至少包括：

| 内容 | 必需字段 |
| --- | --- |
| 当前请求时间 | `serverNow` |
| 配置身份 | `configVersion`、地点标识、城市名、坐标、时区 |
| 站点策略 | 自动／预设模式、预设 ID、季节规则、功能开关 |
| 天气快照 | 统一天气字段、`observedAt/fetchedAt/freshUntil/staleUntil`、新鲜度 |
| 天文信息 | 当地日期、日出日落或计算结果、来源／有效性 |
| 展示归属 | 供应商署名及必要链接 |

天气上游故障时可返回 HTTP 200 的可用环境信封，明确 `weather=null` 或 `freshness=unavailable`；服务自身异常使用正常错误码，前端仍有本地回退。

管理配置采用独立环境模型／服务／DTO，建议内部路由 `GET/PATCH /v1/environment-config`；后台复用现有站点设置页入口，独立提交，避免保存环境设置时覆盖 SEO 或博主资料。管理端 `/api/` 的版本转发与博客端不同，按其 service 和 proxy 约定接入，不照抄公开路径。

建议固定主键 `id='default'` 并使用 upsert，避免 `findFirst()+create` 在并发首次保存时生成多条配置。保存时生成或递增 `revision`，校验管理员权限并使公开配置缓存失效。

天气供应商探测如确有必要，可增加受权限保护的独立操作，禁止公开访客触发强制刷新。单纯通过 JWT 或既有 API Key 认证不代表拥有修改全站配置的权限。

### 6.3 后端与后台模块拆分

以下均为规划模块，不表示现有文件已经存在：

| 模块 | 职责 | 复用边界 |
| --- | --- | --- |
| `EnvironmentConfigService` | 独立单例配置、校验、revision、公开子集、配置缓存失效 | 复用 Prisma 与 ConfigService，不复用 site-config 的一小时响应缓存 |
| `EnvironmentConfigController` | 管理端读取／保存环境配置 | JWT 认证后显式管理员授权；复用异常与日志基础设施 |
| `WeatherProvider` | 供应商查询契约、可选天文信息能力 | 生产首版一个适配器，模拟适配器用于演示和测试 |
| `QWeatherProvider` | 专属 Host、鉴权、响应解析、单位与天气码映射 | 不泄露凭据；不混用新旧版本字段 |
| `WeatherService` | 超时、缓存新鲜度、单次刷新合并、锁、退避和回退 | 可复用 Redis get/set；不使用可能隐式重调上游的 `wrap()` |
| `PublicEnvironmentService` | 组合公开配置、快照、天文信息、即时 `serverNow` | 不缓存整包 serverNow；不持久化访客覆盖 |
| 公开环境控制器 | 提供 `/v1/public/environment` | 可在现有 Public 模块扩展或独立公开控制器，但路径与权限语义保持一致 |
| 后台环境表单／service | 独立获取、预览、保存与错误显示 | 放入现有站点设置导航；不和 SEO 字段一起提交 |

数据库迁移只增加配置及必要版本字段；天气快照首版放缓存，不建立每 15 分钟一条的永久天气历史表。供应商密钥继续由部署侧注入。

## 7. 前端与 Three.js 组件拆分

### 7.1 模块职责

计划新增目录：`apps/blog-web/blog_web/src/components/study/environment/`。

| 模块 | 输入／职责 | 约束 |
| --- | --- | --- |
| `types.ts` | 配置、天气、覆盖和最终状态类型 | 不依赖 Three.js，便于测试 |
| `time.ts` | 显式时区、四时段、太阳数据回退 | 注入时钟，不直接散落 `new Date()` |
| `resolver.ts` | 默认值、博主配置、访客覆盖及异常解析 | 纯函数，同输入同输出 |
| `presets.ts` | 带版本的预设及字段补丁 | 预设不修改真实天气快照 |
| `useEnvironment.ts` | 网络、刷新、取消、存储恢复与配置版本 | 不逐帧 `setState`；卸载可清理 |
| `EnvironmentControls.tsx` | 模式、预设、恢复、台灯及声音设置 | 复用现有设置入口、焦点管理与键盘行为 |
| `EnvironmentStatus.tsx` | 城市时间、天气、新鲜度及预设标签 | 时间更新不反复触发屏幕阅读器播报 |
| `scene-adapter.ts` | `setState/update/setVisibility/dispose` | 由房间拥有生命周期，不创建第二个 renderer |
| `exterior.ts` | 天空、远景、季节植被和灯光蒙版 | 不包含室内家具与窗框 |
| `glass-material.ts` | 干玻璃、雨滴、折射、水痕 | 原型确定是否使用独立低分辨率室外纹理 |
| `precipitation.ts` | 雨／雪粒子、密度、风和空间边界 | 一套可复用缓冲区，避免逐帧创建对象 |
| `audio.ts` | 雨声音轨、音量、交叉淡化与暂停 | 尊重播放手势、全局静音和资源释放 |

这些是逻辑边界，不要求每项都成为 React 组件。3D 网格、材质、粒子留在 Three.js 模块中，React 负责用户交互和低频业务状态。

### 7.2 与现有控制器衔接

- `StudyRoom` 取得最终环境状态后，调用房间控制器的 `setEnvironment(state)`，不卸载重建房间。
- 环境渲染器通过现有 `requestFrame()` 请求绘制；动态效果通过统一的 `needsContinuousFrame` 条件维持动画。
- 业务时间和天气快照可以在渲染暂停时继续更新；被阅读界面遮挡的房间不因此唤醒 GPU。恢复后直接对齐当前状态，不补播后台雨滴。
- 场景每帧只更新低成本 uniform、粒子缓冲区和必要插值，不发网络请求，不做 JSON 解析。
- `setPaused(true)`、页面隐藏、阅读遮挡、减少动态、轻量模式分别作为明确输入；避免暂停背景时误停还在进行的书架导航动画。
- 天气响应、贴图加载和重试携带场景代次及配置版本，迟到回调不能操作已释放的材质或覆盖新城市状态。
- `dispose()` 释放 RenderTarget、纹理、材质、Geometry、音频节点、监听器、请求和定时器；共享资源按所有权管理。

## 8. 天气视觉实施规范

### 8.1 场景层级

从远到近：天空／远景 → 季节植被 → 窗外雨雪 → 玻璃 → 窗框与窗帘 → 室内家具。雨雪不允许穿过墙、窗框或飘进房间。

窗外当前是花园意象，不应因城市配置为杭州就宣称这是博主真实住宅景观。继续保持低对比、柔和、暖橡木书房的美术方向。

### 8.2 晴天

- 调整现有太阳方向光、半球补光、环境强度和曝光，避免同时添加大量新灯。
- 主要识别特征是窗框投影、桌面暖光、墙面柔和色彩，而非全屏泛黄。
- 东向窗的清晨可有明显直射；午后更多依赖天空间接光。首版采用符合朝向的艺术化曲线，不承诺建筑级日照模拟。
- 台灯自动模式按时段和环境亮度驱动，访客手动状态优先；灯光始终保留阅读可见性。
- 太阳／窗帘变化时更新必要阴影。不能让静态阴影缓存保留过期太阳方向，也不应让慢速太阳运动迫使阴影每帧全量刷新。
- 可选云影后补；首版不需要体积光、实时全局光照和大量漂浮尘粒。

### 8.3 多云与阴天

- 多云保留天空亮部和较弱直射，低频调整强度；避免规律闪烁。
- 阴天消除明确直射光束，以偏冷漫射光为主，减小窗外对比和饱和度。
- 不用整屏灰蒙层模拟阴天；文字、按钮和室内材质需要保持清晰。
- 窗帘关闭影响入室光和效果可见性，不改变真实天气状态。

### 8.4 雨天与玻璃折射

拆为窗外雨线、玻璃水滴、水滴折射三个子效果：

| 强度 | 窗外雨线 | 玻璃 |
| --- | --- | --- |
| 小雨 | 稀疏、较细 | 少量静止水珠、偶发滑落 |
| 中雨 | 连续雨线，随风偏斜 | 滑动水滴、小范围水痕和折射 |
| 大雨 | 更密、远景更灰 | 水滴更密、局部更模糊；保持室内内容清楚 |

技术建议：使用同一个 Three.js renderer，在新增窗玻璃网格上实现程序化材质。现有远景是单张贴图，先验证直接采样这张纹理的折射；需要对分层植被和雨雪统一折射时，再增加仅包含室外对象的 RenderTarget。避免默认增加整屋第二遍渲染，或采样整屋截图后把桌面、书本和 UI 折进窗户。

P0 必须验证：

1. 原始贴图远景是否足以支撑水滴折射，是否需要将天空与树冠拆开。
2. RenderTarget 与主相机透视、玻璃 UV、窗口边界的映射是否正确，转头和窄屏时不漂移。
3. 离屏渲染不递归包含玻璃自身，不渲染室内对象；窗框／窗帘遮挡正确。
4. 透明排序、深度写入、抗锯齿和 ACES 色调映射不会导致水滴发黑或边缘出现白边。
5. 手机可以切换成不带折射的少量水滴或静态水痕，而不修改天气语义。

无需完整水动力学。先做到合理水珠形状、速度变化、少量轨迹合并和水痕；复杂聚合是效果增强项。

### 8.5 雪、雾与雷雨

- 雪使用分远近粒子、缓慢下落和少量横摆；近大远小，限制在室外边界。
- 降雪强度与积雪分开。没有雪深或历史依据时，自动模式只表现正在下雪。
- 玻璃冷雾是美术参数，不声称由实时室内外温差精确推导。
- 雾主要作用于室外层的远景、对比和雾密度。禁止直接启用全局场景雾而把近处家具一起罩灰。
- 首版雷雨可以复用大雨视觉、显示雷雨文字；扩展版闪光与雷声独立可关，默认不开强闪。

## 9. 雨声与交互声音

现有书房已有声音开关和翻书等短音效，环境音应接入统一声音策略。建议保留总静音，环境音再有独立音量，不能出现“总声音关闭但雨还在响”。

- 首次访问默认关闭；用户明确点击后创建／恢复音频上下文并按需加载。
- 将用户“希望播放”的意图与音频当前“暂停／加载／播放失败”的状态分开保存，避免沿用隐藏页面即清除声音偏好的旧行为。
- 保存声音偏好不代表浏览器下次一定允许自动播放；被阻止时显示“点击开启雨声”，不循环重试。
- 首版音轨：小雨／中雨／大雨，建议每段 30～60 秒；玻璃敲击点缀可后补。
- 所有音轨需无缝循环、无明显人声、无骤响、无底噪突变；循环接缝和交叉淡化通过耳机试听验收。
- 切换天气或音轨约 1～3 秒淡入淡出；关闭声音立即开始短淡出，不等待天气动画结束。
- 雨停后允许短暂尾声，但不能无限保留雨声。手动雨夜和真实降雨使用同一音频逻辑。
- 页面隐藏暂停；返回后仅在用户偏好与浏览器许可满足时恢复。
- 阅读时用户已经开启的环境音可继续；媒体播放冲突处理采用显式协调事件或用户暂停，不承诺自动检测所有第三方 iframe 声音。
- 音频失败只影响声音，视觉、文章和交互继续工作。

## 10. 后台、权限与运维

后台新增“书房环境”设置分区：

1. 城市显示名、坐标、时区与实时当地时间预览。
2. 自动／博主预设，预设选择与恢复自动。
3. 季节自动／手动、基础台灯策略、雨声是否可用。
4. 当前供应商状态、最近成功时间、天气新鲜度和最近错误摘要；不显示敏感凭据。
5. 保存前使用本地／临时参数预览，不能为预览而修改全站正式配置。
6. 保存复用现有认证，新增明确管理员授权；记录操作者、变更字段、配置 revision 和保存结果，禁止记录密钥。非法时区、坐标、预设 ID 和未知字段拒绝保存；前端隐藏按钮不代替服务端检查。

运维要求与功能直接相关：

- API Host 与供应商选择在部署侧维护，不允许普通公开请求指定目标 URL，避免成为开放代理。
- 为公开接口确认并实际挂载限流能力；现有项目引入 ThrottlerModule 不代表已有全局 ThrottlerGuard。请求合并与上游调用预算仍需独立控制。
- 生产服务器验证 DNS、TLS、上游连通性、真实响应耗时和限额行为；本地可用不代表部署节点可用。
- 日志记录供应商、耗时、缓存命中、退避及失败类型；脱敏请求头、令牌、私钥与完整错误对象。
- 不新建复杂监控平台；在现有结构化日志中可定位“为何用了旧天气／回退”。
- 通过环境功能开关或版本回退可以恢复普通书房，正文与 SEO 路由持续工作。

## 11. 失败回退矩阵

| 故障／边界 | 视觉与 UI | 数据／资源行为 |
| --- | --- | --- |
| 天气请求尚未完成 | 以杭州当前时段显示中性窗景 | 异步请求，首屏和阅读不等待 |
| 上游失败，有合格旧缓存 | 保留相应天气，明确更新延迟 | 退避刷新，不覆盖成功记录 |
| 上游失败，无缓存或旧数据超限 | 当前时段＋中性多云，温度 `—` | `freshness=unavailable`，不伪造实况 |
| 实时天气有效，日出日落失败 | 天气正常，时段采用本地计算或固定表 | 两条数据链路独立 |
| Redis 不可用 | 内存快照或默认窗景 | 有界合并与退避，保护上游配额 |
| 未知天气码／明确提供但错误的时间戳 | 天气不可用，或保留最近有效快照 | 适配失败，不输出 `NaN`；合法缺省的观测时间保持 `null` |
| 城市配置变更时旧请求迟到 | 继续显示新城市状态 | 丢弃配置版本不匹配的响应 |
| 某季节素材加载失败 | 使用基础花园与季节色板 | 不更换成整页错误；可受控重试 |
| 雨滴 shader／RenderTarget 失败 | 禁用折射，保留简化雨景 | 释放故障资源；不持续重编译 |
| 雨声加载／播放失败 | 静音并提示可重试 | 不影响视觉，不重复弹权限提示 |
| 存储被禁用 | 预设和音量仍可在当前内存会话使用 | 捕获存储异常，不阻止操作 |
| 持续掉帧 | 降低环境效果，保留真实天气标签 | 使用现有轻量策略，清理昂贵资源 |
| WebGL 上下文丢失 | 沿用现有恢复／简单界面机制 | 环境资源随场景代次重建，失败后停止重试 |
| 完全无 WebGL | 现有可阅读界面，可选昼夜海报 | 不强行建立新的 renderer |

## 12. 性能与无障碍

### 12.1 档位

沿用用户可见的 `auto/light`；内部可以按能力选择实现，首版不增加难以理解的多级开关。

| 项目 | 自动／设备充足 | 轻量／降级 |
| --- | --- | --- |
| 玻璃雨滴 | 低分辨率折射＋程序化水滴 | 静态水痕或少量无折射水滴 |
| 雨雪粒子 | 有上限的窗外粒子 | 大幅减少或静态替代 |
| 阴影 | 复用现有桌面阴影；本轮增加必要时更新策略，P0 测定成本 | 沿用当前轻量／窄屏策略，不新增高成本阴影 |
| 远景 | 分层贴图与简单植被 | 一张基础远景＋色彩调整 |
| 连续绘制 | 仅可见动态需要时 | 停止装饰性连续绘制；时钟按现有低频规则更新 |

建议验收目标：选定桌面设备以接近 60 FPS 为目标；选定中端手机以稳定约 30 FPS 为目标。必须记录设备、浏览器、分辨率、档位与场景，这些不是当前已达成的性能结论。

实施约束：

- 沿用像素比限制，折射 RenderTarget 建议从窗户屏幕尺寸的约 1/2 分辨率起步，并设最大尺寸；不直接按全屏设备像素比创建多张大纹理。
- 素材按需加载，首次晴天访问不下载完整雨声音轨、雪素材及四季全部高分辨率资产。
- 远景压缩包体不等于显存占用；两张 2048×1024 RGBA 纹理仅基础像素就约占 16 MiB，mipmap 和渲染目标还会增加占用。
- 天气变化进入持续帧采样，避免只有粒子运行时帧率下降却不触发现有自动降级。
- 窗户被完整遮挡、阅读界面完全覆盖房间或页面隐藏时停掉不必要的天气渲染。
- `prefers-reduced-motion` 或用户关闭动态时，雨雪、落叶、云影改为静态表达；不自动关闭用户明确选择的声音。
- 控件键盘可达，面板关闭后恢复焦点；预设状态不只依靠颜色表示。
- 不使用每秒更新的 `aria-live` 播报时钟，不让天气变化反复抢夺焦点。

### 12.2 资源初始预算

以下只作为 P0 优化起点：

- 首屏额外环境 JS 尽量控制在约 100 KB gzip 内；现有 Three.js 不重复打包。
- 基础远景新增网络资源目标不超过约 1 MB；其他季节按需加载。
- 首次开雨声只加载需要的轨道，总音频预算在导出后以实际听感和编码质量校准。
- 切换 20 次预设后 `renderer.info.memory` 和应用持有资源数量应回到稳定区间，不持续线性增长；不要求垃圾回收后进程内存精确回到原值。

### 13.2 制作约束

1. 用户已确认沿用窗外花园与柔和暖色书房；以现有花园构图统一母版，再制作四季变体，不重复询问同一美术方向。不可独立生成四张构图不同的风景后强行淡化。
2. 窗外贴图不包含室内、玻璃雨滴、窗框、窗帘及家具，避免重复和无法分层。
3. 不在远景里烘焙固定强太阳光束或明显窗框投影；时段由灯光和天空参数实现。
4. 季节主要替换植被，时段主要改变天空与灯光，天气通过雾、粒子和玻璃材质组合。无需绘制“四季×四时段×所有天气”的整图矩阵。
5. 颜色纹理标注 sRGB；法线、遮罩等数据纹理不按颜色纹理处理；透明边缘检查白边和黑边。
6. 提供源文件、导出文件、尺寸、透明通道、坐标／UV 对齐说明和裁切安全区。
7. 记录素材作者、来源 URL、许可、署名要求、能否随项目分发；不把演示网页图片或参考图自动当成可部署资产。
8. 统一美术风格：浅暖橡木、米白墙面、柔和阴影、低对比窗外；效果服务于书房与阅读。

建议资产目录：`public/study-assets/environment/` 下分 `exterior/seasonal/glass/snow/audio/fallback`。正式文件使用版本或内容哈希，并与现有 `/study-assets/` 缓存规则一致。

| T20 | 生产节点请求、实际 Nginx 路径、无 Key／配额耗尽 | 正常路由与鉴权可用；外部失败可回退；正文与 SEO 不依赖天气 | 首版 |

建议自动化覆盖纯状态解析、时区边界、供应商映射、缓存生命周期、配置竞态和资源清理；视觉与声音用固定参数的截图／真机／耳机验收。不要为 shader 每个内部常量编写重复实现的单元测试。
